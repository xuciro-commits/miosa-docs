每个人都懂 Markdown 的语法，但几乎没人知道我们把它渲染成了什么。结果就是：同一个意思，有人写成加粗段落，有人写成表格，有人写成列表，读起来像三份不同的文档。

这份手册解决的就是这件事：**把"语义"从语法里补回来**。标准 Markdown 只描述"这是列表、这是表格"，不描述"这是一张导航卡、这是一条注意、这是一组可选命令"。我们给后者起了名字，并把它们映射到已经存在的组件上。

## 三层模型

| 层 | 由谁决定 | 例子 |
|---|---|---|
| 内容层 | 标题层级与正文顺序 | H1=页面、H2=章节、H3=条目 |
| 块层 | 段落标记的形状 | 表格、代码块、引用块、列表 |
| 版面层 | frontmatter 的 `layout` 字段 | `cards`、`accordion`、`collection` |

三层分开的好处是：内容层保证结构对等（中英双语必须同构），块层保证可读性（不渲染也读得通），版面层保证阅读优化（渲染后更好读）。任何一层出问题，都能单独修。

## 三条设计原则

1. **语义优先**：不要用加粗伪装标题，也不要用列表伪装表格。语法形状要与语义一致，渲染器才知道该做什么。
2. **可退化**：所有约定都必须在不渲染时仍然可读。`- [标题](链接): 描述` 去掉渲染就是一条普通列表，不会变成乱码。
3. **少即是多**：能用表格解决的，不要引入新块。目前全站只有三种版面标记，新增任何一种都要先证明现有三种做不到。

## 为什么需要变体渲染

因为阅读场景不是一种。导航页要一次扫到十个入口，参考页要逐条查参数，教程要按顺序执行命令，测验页要隐藏答案。同一种文本形状无法同时满足这四种需求，而标准 Markdown 又没有"这是导航页"这种元信息。

变体渲染补的就是这个缺口：**版面由声明决定，而不是由猜测决定**。声明写在 frontmatter 里，读者看不见，作者一眼看懂，CI 还能校验。
